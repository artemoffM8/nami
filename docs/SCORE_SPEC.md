## 1. Сверка с тем, что уже заложено

Прежде чем задавать новую математику, выписываю действующие формулы из кода.
Очки обязаны с ними согласовываться, а не жить параллельной жизнью.

### 1.1 Рейтинг ясности (`RatingEngine`, `rating-v2.0`)

```
E  = 1 / (1 + 10^((D − R) / 400))
ΔR = K × (S − E),  S ∈ {0, 1}
K  = 48 при < 5 применённых результатах, 32 при < 15, дальше 20
ΔR ∈ [−12, +28],  R ≥ 600,  старт 1000
калибровка = 3 результата
```

### 1.2 Штрафы помощи (`AssistanceUsageLedger`) — доли, не очки

| Источник | Уровни и штраф |
|---|---|
| `candidateAid` | нет 0 · панель 0.02 · линза 0.06 · выбранная 0.08 · всё поле 0.12 |
| `hintLayer` | нет 0 · область 0.03 · техника 0.06 · логика 0.14 · **reveal 0.00** |
| `validationAid` | нет 0 · заметка 0.02 · одиночка 0.03 · проверка 0.04 · сверка 0.06 |

```
assistPenalty = min(сумма трёх, 0.24)
guessPenalty  = min(strikes × 0.06, 0.12)
```

Три вещи здесь важны и легко упускаются:

- **Журнал монотонен.** Хранится достигнутый УРОВЕНЬ, а не число нажатий.
  Десять проверок стоят столько же, сколько одна.
- **`reveal` стоит 0.00** не по доброте: он делает партию нерейтинговой целиком,
  поэтому штрафовать нечего.
- **Третий подтверждённый strike** переводит партию в тренировочную, поэтому
  `guessPenalty` и упирается в 0.12 — больше двух ошибок рейтинг не видит.

### 1.3 Темп (`speedBucket`)

```
ratio = activeSeconds / expectedActiveSecondsP50
ratio ≤ 0.70 → 3     ≤ 0.85 → 2     ...     иначе 0
```

Бакет даёт `speedBonus` только в плюс и только в испытании «Против рекорда».

### 1.4 Жёсткие ограничения продукта

- **Медленное решение не наказывается никогда.** Время не может уменьшать
  ни рейтинг, ни очки. Только прибавлять бонус.
- **Ошибка не звучит и не выглядит упрёком.** Звук конфликта на 6% громкости,
  без вспышек и красных всплесков.
- **Понижение не празднуется и не наказывается визуально** — спокойное
  перетекание.
- **В «Бумаге» приложение молчит.** Оно не сверяет ввод с решением, поэтому
  не знает о неверной цифре, пока та не конфликтует по правилам.

## 2. Что не так с моей первой реализацией

Я задал множителю собственную таблицу: ×0.80 за ошибку, ×0.92 / ×0.85 / ×0.75
за слои подсказки, ×0.95 за проверку. Числа взяты с потолка и **не связаны**
с 1.2. Получилось две независимые шкалы наказаний за одно и то же действие.

Правильно — вывести множитель из уже существующего журнала. Тогда экран
результата может сказать одно связное предложение: «помощь стоила вам 18%
рейтингового прироста и 36% множителя», и оба числа будут из одного источника.

## 3. Точная математика множителя

### 3.1 Базовый множитель по тиру

```
easy 100 · medium 150 · hard 200 · expert 280 · master 400
```

Сложная задача обязана давать больше за тот же ход, иначе выгодно фармить лёгкие.

### 3.2 Итоговый коэффициент

```
assistDrag = ledger.assistPenalty × 2.0            → 0 … 0.48
guessDrag  = min(errors × 0.08, 0.32)              → 0 … 0.32
churnDrag  = min(max(0, rewrites − 1) × 0.05, 0.20) → 0 … 0.20

factor     = clamp(1 − assistDrag − guessDrag − churnDrag, 0.25, 1.0)
multiplier = round(base(tier) × factor)
```

Три решения внутри:

- **Коэффициент 2.0** — очки чувствительнее рейтинга ровно вдвое. Это осознанно:
  рейтинг медленный и терпимый, очки — быстрый и заметный слой. Один и тот же
  журнал, разная громкость.
- **`errors` считает ВСЕ ошибки, а не первые две.** Рейтинг после третьей
  просто перестаёт применяться; очки продолжаются до конца партии, поэтому им
  нужна своя шкала.
- **Пол 0.25.** Ниже множитель не падает: доиграть до конца должно оставаться
  осмысленным даже в провальной партии.

### 3.3 Особый случай reveal

```
если ledger.revealUsed → factor = 0.25 немедленно
```

В рейтинге `reveal` стоит 0.00, потому что снимает рейтинг целиком. В очках
такой трюк не работает — очки остаются. Поэтому reveal сразу опускает множитель
на пол. Открыть цифру можно, но платить за это будет вся оставшаяся партия.

## 4. Начисления

| Событие | Очки |
|---|---|
| Верная цифра | `3 × multiplier` |
| Закрытая строка, столбец или блок | `10 × multiplier` за каждую |
| Задача решена | `50 × multiplier` |
| Бонус темпа | `speedBucket × 20 × multiplier` |

Начисление считается по множителю **на момент события**. Ошибка снижает
множитель для будущих ходов и никогда не отнимает уже набранное — отнимать
заработанное ощущается как обман.

Полная чистая партия «Сложно» (51 пустая клетка, 27 групп):

```
51 × 3 × 200  = 30 600
27 × 10 × 200 = 54 000
     50 × 200 = 10 000
                ───────
                 94 600
```

## 5. Защита от угадывания

Здесь главная дыра, и она не в математике.

**В «Бумаге» и «Фокусе» приложение не сверяет ввод с решением.** Игрок,
подбирающий цифры так, чтобы они не конфликтовали по правилам, не получает
ни одного strike — и уносит полный множитель. Штраф за ошибки работает только
в «Ассистенте».

Поэтому нужен признак угадывания, не требующий знания решения.

### 5.1 Перезапись клетки (`churnDrag`)

Считаем, сколько РАЗНЫХ цифр побывало в одной клетке за партию.

```
rewrites = Σ по клеткам max(0, различных_значений − 1)
churnDrag = min(rewrites × 0.05, 0.20)
```

Одна замена — нормальная правка. Третья и четвёртая разная цифра в одной
клетке — перебор, независимо от профиля помощи. Порог мягкий и потолок низкий:
это не должно наказывать нормальную работу с заметками.

### 5.2 Что уже есть и переиспользуется

- `evaluateGuessGuard` — предложение «попробовать заметки» после
  подтверждённой ошибки;
- `StruggleDetector.repeatedUndo` — четыре отката за 45 секунд;
- третий strike → тренировочная партия.

### 5.3 Чего сознательно НЕ делаем

Не проверяем каждый ход солвером на «выводим ли он логически». Это честный
детектор угадывания, но он требует `HumanSolver.nextStep` на каждое касание —
а бюджет P95 на ход по критерию 23 составляет 100 мс.

## 6. Анимации

| Что | Как | Длительность |
|---|---|---|
| Прирост очков | счётчик «набегает», не прыгает | 250 мс, `easeOut` |
| Падение множителя | старое значение гаснет, новое проявляется | 200 мс, без вспышки |
| Бонус за группу | прирост появляется вместе с `lineWave`/`boxBloom` | 210 / 260 мс |
| Итог партии | счётчик добегает ДО победной волны | 400 мс, затем `boardWave` 800 мс |

Правила, которые нельзя нарушать:

- **Ни красного, ни тряски при падении множителя.** Ошибка в NAMI не ругает.
- **Счётчик не анимируется во время `boardWave`** — два движения одновременно
  превращают финал в шум.
- **Reduce Motion**: счётчик меняется мгновенно, остаётся только 160 мс fade.
- Оверлей очков `allowsHitTesting(false)` — анимация никогда не съедает касание.

## 7. Итоговый экран

Порядок сверху вниз:

1. Крупное число очков.
2. Подпись «Очки за партию».
3. Разбор в строку: верные цифры · закрытые группы · ошибки · итоговый множитель.
4. Сноска «Время на очки не влияет — только угадывание и помощь».
5. Ниже — существующий блок рейтинга ясности с его собственным разбором.
6. Прогресс калибровки, если она ещё идёт.

Два числа рядом требуют, чтобы разница между ними была объяснена одной строкой,
иначе игрок будет считать их одним и тем же.

## 8. Примеры расчёта

### Пример A. Чистая партия «Средне», без помощи

```
assistPenalty 0 → assistDrag 0
errors 0        → guessDrag  0
rewrites 0      → churnDrag  0
factor 1.00, multiplier 150

45 цифр × 3 × 150 = 20 250
27 групп × 10 × 150 = 40 500
решение 50 × 150 = 7 500
ИТОГО 68 250
```

### Пример B. «Сложно», линза + подсказка до техники + две ошибки

```
candidateAid .lens        0.06
hintLayer .techniqueName  0.06
validationAid .manualCheck 0.04
assistPenalty = 0.16 → assistDrag 0.32
errors 2             → guessDrag  0.16
rewrites 3           → churnDrag  0.15
factor = 1 − 0.63 = 0.37,  multiplier = round(200 × 0.37) = 74
```

Множитель упал с 200 до 74 — почти втрое. Рейтинг при этом потерял
`assistPenalty 0.16 + guessPenalty 0.12 = 0.28` прироста. Обе цифры выводятся
из одного журнала, и это видно на экране.

### Пример C. Открыта цифра

```
revealUsed → factor 0.25, multiplier = 50 (для «Сложно»)
рейтинг: партия нерейтинговая, ΔR = 0
очки: продолжают начисляться на четверти множителя
```

## 9. События для Xcode

Домен публикует семантику, слой представления решает, как её показать.

### 9.1 Новые случаи `GameEvent`

```swift
case scoreAwarded(points: Int, total: Int, source: ScoreSource)
case multiplierDropped(from: Int, to: Int, reason: MultiplierDropReason)

enum ScoreSource { case placement, group, completion, pace }
enum MultiplierDropReason { case error, hint, check, candidateAid, reveal, churn }
```

Приоритет в `FeedbackTransaction`: `scoreAwarded` = 2 (наравне с `digitPlaced`),
`multiplierDropped` = 3 (наравне с `conflictDetected`) — падение множителя важнее
прироста, но не важнее закрытой группы.

### 9.2 Отображение в `FeedbackCoordinator`

| Событие | Анимация | Звук | Haptic |
|---|---|---|---|
| `scoreAwarded(.placement)` | `.none` (счётчик сам) | наследует `digitPlaced` | наследует |
| `scoreAwarded(.group)` | наследует `lineWave` / `boxBloom` | `groupCompleted` | `groupTransient` |
| `scoreAwarded(.completion)` | `.boardWave` | `victory` | `.success` |
| `multiplierDropped` | `.fade` | **`.none`** | **`.none`** |

`multiplierDropped` намеренно немой: звук уже отыграл конфликт, второй сигнал
на то же действие превращает ошибку в наказание.

### 9.3 Что проверять в Xcode

- счётчик добегает до победной волны, а не поверх неё;
- при Reduce Motion число меняется без анимации;
- множитель не опускается ниже 25% базового ни при каком наборе действий;
- в «Релаксе» блока очков нет вообще — ни в HUD, ни на результате;
- VoiceOver читает очки одной меткой «Очки, 12 300», а не по частям.

## 10. Что нужно решить вам

1. **Коэффициент чувствительности 2.0** — очки вдвое строже рейтинга. Больше
   сделает партии с помощью бессмысленными, меньше — незаметными.
2. **Пол множителя 0.25.** Ниже — партия перестаёт иметь смысл.
3. **`churnDrag`** — единственная защита от угадывания в «Бумаге». Порог
   «третья разная цифра в клетке» может задевать вдумчивую игру с заметками.
4. Нужны ли очки в **Daily** или там остаётся `DailyScore` с вычитанием времени.
